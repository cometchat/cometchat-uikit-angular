# UI Kit Angular 5.3.0: offline support (release notes draft)

Status: draft for the 5.3.0 release.

## Dependency

- Offline support needs **Chat SDK JavaScript 4.3.1** or later. The peer dependency stays `^4.2.0`: the kit
  feature-detects every offline SDK member at runtime, so an app pinned to 4.2.x or 4.3.0 keeps working with offline off
  (no `ERESOLVE` on upgrade).
- Angular 5.x only. UI Kit 4.x (`legacy`) gets no offline support; turning the SDK's offline on with it is unsupported.

## Added (all optional; offline off by default)

- `UIKitSettingsBuilder.setOfflineConfig(config)`, `UIKitSettings.offlineConfig`, the structural `CometChatOfflineConfig`
  type; `chatSDK.offline` in `initFromSettings` reaches the SDK unchanged, and `CometChatUIKit.initFromSettings(settings,
  offlineConfig?)` (internal, the AI agent path) takes the same offline config as `init`, which wins over the file's.
- `CometChatMessageEvents.ccMessageSendStateChanged` (`IMessageSendStateChanged`) and
  `CometChatMessageEvents.ccOfflineCacheReset` (`IOfflineCacheReset`). Never emitted with offline off.
- `hideOfflineNotices` input on `cometchat-message-list` and `cometchat-conversations`.
- `CometChatUIKitConstants.MessageOption.retryMessage` and `.discardMessage` (option ids on unsent messages).
- Offline strings in all 19 locales, with plural forms (`_one`/`_few`/`_many`/`_other`).
- `ConnectionStateService.connects$`: every connect the SDK reports, whether or not it changes the connection
  state and whether or not a disconnect was reported first. The message list reloads a chat it could not load
  on this, because the state does not change across a drop the SDK never reported. The service also follows the
  browser's own `online`/`offline` events as a backstop, and neither handler acts against the SDK's own
  `getConnectionStatus()`.
- CSS variables for the offline states (see the Offline Support page, Theming).
- Automation identifiers (see "Offline-OFF behaviour changes"): `data-testid` / `data-cc-*` on message rows, the row
  menu, conversation rows, notices, the list footer, the composer input, tray tiles and the empty/error views.

## Behaviour with offline on

- Cached first paint, then the server page in place, on the message list, conversation list, users, groups, group
  members, reactions, notification feed, pinned, saved and AI history.
- Own sends show "Not sent yet" until sent; failures are derived from the SDK's status (they survive a restart).
- Own unsent messages show the clock with **Not sent yet** next to it.
- Every own unsent or failed message (PENDING, SENDING, or FAILED for any reason) offers Retry and Delete, and nothing
  that needs a server id: no reply, thread, react, edit, pin, save, info or Copy (ruling R162 / S73, BEH-SEND-37 as
  rewritten on 2026-11-03). A failed message always shows **Not sent. Tap to retry**. Retry or Delete on a message
  whose send is already under way changes nothing: the SDK answers `ERROR_OFFLINE_MESSAGE_IN_FLIGHT` and the list shows
  a short **Sending… try again in a moment** notice (one at a time, gone after 4 seconds; new string
  `message_list_send_in_flight` in all 19 locales). Delete keeps today's confirmation dialog, then uses the SDK's
  `discardLocalMessage` (device only, durable).
- When the session ends (logout or user switch) or the offline cache resets, open `CometChatUIKit.send*` promises reject once and quietly with the code `ERROR_OFFLINE_MESSAGE_DISCARDED` (the same as Android, React and React Native). The failure `reason` stays `DISCARDED`. The kit treats both this code and the older `DISCARDED` as quiet.
- Tapping an image, video or file the SDK has no copy of, while connected, asks the SDK to download and cache it. Playing an audio file does the same; the audio keeps playing from its URL and uses the cached copy the next time it loads.
- Group actions missed while away (kick, ban, scope change, leave from another device) come only in the SDK's
  catch-up. The kit runs its own live handlers for them and also emits the existing `CometChatGroupEvents`
  (`ccGroupMemberKicked`, `ccGroupMemberBanned`, `ccGroupMemberScopeChanged`, and `ccGroupLeft` when the signed-in
  user left elsewhere), with the same payload shape. **Integrators:** with offline on these events no longer always
  mean "this user just did it": check `kickedBy` / `message.getActionBy()` before showing an own-action toast, and
  handle `kickedUser` being the signed-in user (close the chat) as your SDK `GroupListener` does. No new API.
- On reconnect the message and conversation lists make no refresh fetch of their own; the SDK's catch-up is consumed.
  The only reads the kit starts by itself are the first page of a list that shows its offline state, a search that
  shows **Connect to search**, and the page behind a **Connect to load more** row; each runs once.
- The message list's default request sends only `hideReplies` for a top-level chat, because Chat SDK JavaScript 4.3
  saves a fetched page for offline only then. The kit applies the default types and categories itself, so the same
  messages show as today. With offline off the request is unchanged. A list with your own `messagesRequestBuilder`
  is sent as you built it, so if it sets other filters the SDK does not save its pages.
- Offline, a read past the saved messages shows a tappable **Connect to load more** row at that edge (the top for
  older messages, the bottom for newer ones; the text was **Connect to load older messages** in earlier drafts of this
  release, and the key `message_list_connect_to_load_more` is unchanged) and never ends the list. When the connection is
  back, the page behind the row loads once by itself, the older edge first; tapping the row or scrolling to that end
  also reads (one read per gesture, at most once a second). A read that fails for any other reason (a server error) does
  not end the list either: the next scroll or tap reads again.
- Offline states and errors on every list (ruling D84, which replaces D83), with offline on. Users, groups, group
  members, conversations, the message list and threads, the reactions list, pinned, saved, the notification feed and
  search follow one rule.
  - Offline with nothing on screen, a list shows its offline state, an icon with **Connect to load users / groups /
    chats / members / messages / reactions / notifications** and no Retry button. If you passed an error view, it
    shows instead. The list's error output fires once. The list loads once by itself when the connection is back.
  - A keyword search that cannot run offline, with no saved match, shows **Connect to search** and a second line,
    **Search needs an internet connection.** It is an offline state, so the error output does not fire, and the search
    runs again once when the connection is back. A list opened with only a filter (online users, tags, a builder or
    request with no keyword) is a plain list: it shows **Connect to load users** (or that list's text). In the Search
    component, with both scopes, **Connect to search** shows only when every failed request was a not-connected one; a
    mix with a server error is the normal error view. The Search component follows the Android UI Kit here: a search
    by filter alone is answered from the device, and when it cannot reach the server with nothing saved it shows the
    plain empty state (**No Results**), not **Connect to search**, with no error output and no run on reconnect. Its
    **Connect to search** reads `search_connect_to_search_messages`, the text Android's search screen uses.
    The Search component also waits for both scopes before it calls a failure an error, as Android does. When both
    scopes fail, at least one with a real error, it shows the error view and the error output fires for each. When only
    one scope fails with a real error and nothing is shown, it shows the plain empty state (**No Results**, or your own
    empty view), with no error output and no run on reconnect; if the other scope has results they stay and the failure
    still reaches the error output once. Searching one scope only (a chat's own search, or `searchIn` of one) follows
    the same rule. With offline off nothing changes.
  - Online, a real error with nothing on screen is the error view with Retry (yours, if you passed one) and the error
    output fires once. It is not reloaded by itself.
  - Rows on screen stay with nothing over them. Offline reports nothing. Online, a load the user or app started
    (opening, pull-to-refresh, a search or filter, paging, a jump to a message, Retry) fires the error output once, and
    a load the kit started (reconnect, sync, cache reset) stays silent.
  - A server that answers an empty list shows the empty view.
  - This restores the "Connect to load users / groups / chats / members" and "Connect to search" states of earlier
    drafts of this release (never published), with the strings `users_connect_to_load`, `groups_connect_to_load`,
    `conversations_connect_to_load`, `group_members_connect_to_load` and the identifiers `data-cc-reason="connect-to-load"`
    and `"connect-to-search"` (`data-testid="cc-empty"`), and adds `message_list_connect_to_load`,
    `reaction_list_connect_to_load`, `notification_feed_connect_to_load` and `list_connect_to_search_subtitle`. The
    `connectToSearchChange` output of earlier drafts stays removed. The composer's mention-popup stays as in D83: a
    mention search that fails offline is "no match" and the popup closes. A chat opened offline with nothing saved
    shows **Connect to load messages**, not the empty view with the footer.
  - In every language the Android UI Kit also ships (all but en-gb, which is English), these strings are the text
    Android uses for the same state, so the two kits read the same.
- Nobody shows as online while the connection is down, in any list or header. Screen readers do not announce a user as
  online in the users list either.
- Start from the first unread message, with offline on: the chat opens on its newest page, which paints from the
  device, and is then positioned on the unread divider (jumping there when the unread run starts earlier). Neither
  scroll observer pages until the list is positioned.
- A send the queue refuses (`maxPendingMessages` reached, or a file over the offline byte budget) shows as not sent with
  one notice (**Too many messages waiting to send**, or **File too large to send offline**), whichever of the SDK's two
  reports of the refusal arrives first.
- A photo, video or file picked or dropped while not connected skips the tray, whose upload cannot start, and goes to
  the SDK's queue: its row shows at once and it sends on reconnect. Connected, the tray works as today.
- A cache-reset notice shows even when the SDK reports the reset before the app has bootstrapped. `ENCRYPTION_CHANGED`
  adds no notice of its own: each lost message already has one.

## Defect fixes visible with offline off

- D1: the conversation list's reconnect refresh keeps the fetched copy of a row (it kept the stale one).
- D3: a failed composer send shows the error mark instead of the clock (metadata is merged, not replaced). The failed
  row gets a new object reference.
- D4: the server copy of an own message replaces the local one and keeps the thread-subscribed flag and quote.
- D7: a consumer-supplied `messagesRequestBuilder` is no longer mutated.

## Offline-OFF behaviour changes in this minor

- D6: `CometChatUIKit.sendTextMessage/sendMediaMessage/sendCustomMessage` merge `metadata.error` into existing metadata
  on failure instead of replacing it (the error event's payload keeps integrator keys); `metadata.error` stays present.
- Automation identifiers ship with offline off too. Message rows gain `data-testid="cc-message-row"`, `data-cc-key`,
  `data-cc-id`, `data-cc-state` and `data-cc-mine` (`cometchat-message-list.component.html:170`). Also new: `cc-message-options`
  (`data-cc-options`), `cc-conversation-row` (`data-cc-with`, `data-cc-unread`, `data-cc-pinned`, `data-cc-preview-state`),
  `cc-composer-input`, `cc-composer-tray-tile` (`data-cc-file-id`, `data-cc-index`, `data-cc-state`), `cc-empty` and
  `cc-error` (`data-cc-reason`). They are DOM additions only: no message text, not read by screen readers. Integrators'
  DOM snapshot tests may change.
- The root `ConnectionStateService` now follows the browser's `online`/`offline` events as well as the SDK's, with
  offline off too. After a drop the SDK does not report, the next connect therefore counts as a reconnect, and the
  lists that refetch on reconnect (Conversations, Users, Groups, Group Members, Pinned, Saved, search) each make one
  extra read where 5.2.3 made none. Nothing is refetched while the SDK reports its socket as connected, and a drop
  before the first connect is ignored, so a sign-in is never treated as a reconnect.

These ship in this minor rather than an earlier patch release, as decided on 2026-11-02.

## Bundle size

Chat SDK 4.3 adds 0.54 MB to an app's initial bundle and this kit adds 0.12 MB, with offline on or off. The sample app's
initial bundle goes from 4.53 MB to 5.20 MB, so its budget moves from 5 MB to 5.5 MB.

## Known issues (until the SDK changes)

- A lost send acknowledgement can create one server-side duplicate (BEH-SEND-23).
- Missed messages can appear up to one sweep cooldown (10 s) after a quick reconnect.
- After a restart a failed message's reason may be unknown; it is offered Retry.
- A chat can stall while online when a send got no answer while connected; it resumes at the next reconnect (R94).
- Editing, reacting to or deleting an already-sent message needs a connection: no SDK queues these actions, so offline
  the action is refused and the message stays as it is. The UI reports the failure. A queued message that has not gone
  out yet can still be retried or deleted offline.
- A reconnect the SDK does not report can leave a queued message on **Not sent yet**: the SDK can re-establish its
  session without reporting `onConnected`, which is the event the kit flushes on. A reload clears it. The kit now
  covers the two cases it can: it reloads a message list on any connect the SDK reports rather than only on one that
  followed a reported disconnect, and it takes the browser's own `online` event as a connect when the SDK's socket is
  already up. A session re-established with no SDK event and no browser event left is what remains.
- The Chat SDK's own send Promise may never settle when the session ends; the kit does not wait on it.
  `CometChatUIKit.send*` promises still settle: they reject once with `ERROR_OFFLINE_MESSAGE_DISCARDED` (see above).
- Multi-tab: one tab's rebuild can discard another tab's sends; that tab's rows update from the outbox events.
- With offline off the message list makes no read of its own on reconnect, as in 5.2.2: its connection listener has
  never been attached (`setupConnectionListener` has no caller), so messages missed during a drop appear when the chat
  is reopened.
- Keyword search, message information, call logs and AI streamed replies need a connection.
- A thread opened online is not saved for offline: the SDK does not cache a page read with a parent message id.
- The browser cache encrypts content but not lookup metadata; downloaded media is stored unencrypted.
